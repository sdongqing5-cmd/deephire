# Phase 1: 技术选型详细说明

## 1. 前端技术栈

### 1.1 核心框架

| 技术 | 版本 | 用途 | 为什么选择 |
|------|------|------|------------|
| **Next.js** | 15.x | React 框架 | • SSR 支持，SEO 友好<br>• App Router，路由简单<br>• 自动代码分割<br>• 图片优化<br>• API Routes 支持 |
| **React** | 19.x | UI 库 | • 生态成熟<br>• 组件化开发<br>• 性能优秀 |
| **TypeScript** | 5.x | 类型系统 | • 类型安全<br>• IDE 支持好<br>• 重构友好<br>• 减少 bug |

### 1.2 UI 与样式

| 技术 | 版本 | 用途 | 为什么选择 |
|------|------|------|------------|
| **Tailwind CSS** | 3.x | CSS 框架 | • 快速开发<br>• 一致性好<br>• 文件体积小<br>• 不需要写 CSS |
| **shadcn/ui** | latest | 组件库 | • 高质量组件<br>• 完全可定制<br>• 复制到项目中，不是 npm 包<br>• 基于 Radix UI，无障碍性好 |
| **Radix UI** | latest | 无头组件 | • shadcn/ui 的底层<br>• 无障碍性优秀<br>• 行为完善 |
| **framer-motion** | 11.x | 动画库 | • 声明式动画<br>• 性能好<br>• 手势支持<br>• 适合微交互 |
| **lucide-react** | latest | 图标库 | • 图标美观<br>• Tree-shakable<br>• 与 shadcn/ui 配套 |

### 1.3 状态管理

| 技术 | 版本 | 用途 | 为什么选择 |
|------|------|------|------------|
| **TanStack Query** | 5.x | 服务端状态 | • 自动缓存<br>• 自动重试<br>• 乐观更新<br>• 轮询支持<br>• 比 Redux 简单 |
| **Zustand** | 4.x | 客户端状态 | • 轻量（1KB）<br>• API 简单<br>• 不需要 Provider<br>• TypeScript 支持好 |

**为什么不用 Redux？**
- Redux 太重，学习曲线陡
- TanStack Query 已经解决了 90% 的状态管理问题
- Zustand 足够处理剩下的 10%

### 1.4 表单处理

| 技术 | 版本 | 用途 | 为什么选择 |
|------|------|------|------------|
| **React Hook Form** | 7.x | 表单管理 | • 性能好（非受控）<br>• API 简单<br>• 与 Zod 集成好 |
| **Zod** | 3.x | 数据验证 | • 类型安全<br>• 错误信息友好<br>• 与 TypeScript 完美集成 |

### 1.5 HTTP 客户端

| 技术 | 版本 | 用途 | 为什么选择 |
|------|------|------|------------|
| **Axios** | 1.x | HTTP 请求 | • 拦截器支持<br>• 自动转换 JSON<br>• 取消请求<br>• 比 fetch 功能多 |

### 1.6 工具库

| 技术 | 版本 | 用途 |
|------|------|------|
| **date-fns** | 3.x | 日期处理 |
| **clsx** | 2.x | 类名合并 |
| **tailwind-merge** | 2.x | Tailwind 类名合并 |

## 2. 后端技术栈

### 2.1 核心框架

| 技术 | 版本 | 用途 | 为什么选择 |
|------|------|------|------------|
| **Python** | 3.12 | 编程语言 | • AI 生态丰富<br>• 简历解析库多<br>• 开发效率高 |
| **FastAPI** | 0.115+ | Web 框架 | • 高性能（基于 Starlette）<br>• 自动生成 OpenAPI 文档<br>• 类型提示支持<br>• 异步支持<br>• 依赖注入 |
| **Uvicorn** | 0.30+ | ASGI 服务器 | • 高性能<br>• 支持 HTTP/2<br>• 支持 WebSocket |

**为什么不用 Django？**
- Django 太重，包含太多不需要的功能
- FastAPI 性能更好（3-4倍）
- FastAPI 的异步支持更好

**为什么不用 Flask？**
- Flask 是同步框架，性能较差
- FastAPI 有自动文档生成
- FastAPI 的类型提示更好

### 2.2 数据库相关

| 技术 | 版本 | 用途 | 为什么选择 |
|------|------|------|------------|
| **SQLAlchemy** | 2.0 | ORM | • 成熟稳定<br>• 功能强大<br>• 2.0 版本性能提升<br>• 异步支持 |
| **Alembic** | 1.13 | 数据库迁移 | • SQLAlchemy 官方工具<br>• 版本管理<br>• 自动生成迁移 |
| **asyncpg** | 0.29 | PostgreSQL 驱动 | • 异步驱动<br>• 性能最好 |
| **psycopg2** | 2.9 | PostgreSQL 驱动 | • 同步驱动（备用）<br>• 成熟稳定 |

### 2.3 数据验证

| 技术 | 版本 | 用途 | 为什么选择 |
|------|------|------|------------|
| **Pydantic** | 2.x | 数据验证 | • FastAPI 内置<br>• 类型安全<br>• 自动文档生成<br>• 性能好（2.0 用 Rust 重写） |

### 2.4 认证与安全

| 技术 | 版本 | 用途 | 为什么选择 |

### 2.7 搜索相关

| 技术 | 版本 | 用途 | 为什么选择 |
|------|------|------|------------|
| **opensearch-py** | 2.x | OpenSearch 客户端 | • 官方客户端<br>• 异步支持 |

**第一版可以不用 Celery**：
- 简单的异步任务可以用 FastAPI 的 BackgroundTasks

## 8. 为什么这个技术栈？

### 8.1 开发效率

✅ **前端**：Next.js + shadcn/ui = 快速开发
✅ **后端**：FastAPI + SQLAlchemy = 快速开发
✅ **类型安全**：TypeScript + Pydantic = 减少 bug

### 8.2 性能

✅ **前端**：Next.js SSR + 代码分割
✅ **后端**：FastAPI 异步 + Redis 缓存
✅ **搜索**：OpenSearch Hybrid Search

### 8.3 可扩展性

✅ **数据库**：PostgreSQL 可扩展到百万级
✅ **搜索**：OpenSearch 可集群化
✅ **架构**：Monolith → 微服务（未来）

### 8.4 成本

✅ **全部开源**：无许可证费用
✅ **运维简单**：Docker 部署
✅ **学习曲线**：主流技术，容易招人

## 9. 技术风险

### 9.1 OpenSearch

**风险**：团队可能不熟悉
**缓解**：
- 提供详细文档
- 第一版用简单配置
- 可以先用 PostgreSQL 全文搜索

### 9.2 AI 成本

**风险**：OpenAI API 成本高
**缓解**：
- 使用 GPT-4o-mini（便宜）
- 缓存解析结果
- 后续可以用开源模型

### 9.3 向量搜索

**风险**：向量生成成本高
**缓解**：
- 第一版可以只用 BM25
- 后续再加向量搜索
- 使用本地模型（sentence-transformers）

---

## 10. 技术选型原则

1. **优先选择主流技术**：容易招人，社区支持好
2. **优先选择开源技术**：降低成本
3. **优先选择成熟技术**：减少风险
4. **优先选择简单技术**：快速开发
5. **保持可扩展性**：未来可升级
